这篇记录一组本机实验，不把单卡结果包装成通用结论。硬件是 22GB 的 RTX 2080 Ti，架构为 Turing / SM75，模型是 Qwen3.5-9B AWQ。

## 先把显存账算清楚

推理时显存至少要分给三部分：

- 模型权重；
- KV Cache 或混合架构里的状态池；
- CUDA context、计算缓冲和推测解码等固定开销。

实验中 Qwen3.5-9B AWQ 的 LLM-only 权重约 10.35 GiB，适合作为单卡实验台；大多数 27B AWQ/INT4 权重在 19～22GB，已经超过这张卡的实际余量。

## 速度基线

在 8K 上下文、单序列、生成 256 tokens 的条件下，得到如下结果：

| 配置 | 速度 |
| --- | ---: |
| eager 基线 | 41.0 tok/s |
| 加入 CUDA Graph | 46.1 tok/s |
| MTP_K=2 | 80.3 tok/s |
| 只提高 MAX_BATCHED_TOKENS | 80.8 tok/s |

这组结果说明，当前配置里影响最大的不是继续调 batch，而是减少每个 token 的主模型读取次数。MAX_BATCHED_TOKENS 从 2048 带来的变化落在噪声范围内，没必要把它当成主要优化方向。

## 长上下文并不总是昂贵

在混合注意力架构下，262K 上下文的实测显存约 21998 / 22528 MiB，生成速度 38.6 tok/s，相比短上下文只下降约 6%。

但 MTP 和超长上下文并不能同时无限开启：MTP 的验证工作区会占用额外 KV 空间，长上下文已经把显存余量吃得很干净。

## Prefix Cache 的效果

对约 6.9K tokens 的长前缀做冷、热请求对比：

- 冷请求：3.30s；
- 热请求：0.71s；
- 速度约提升 4.6 倍；
- 引擎 hit rate 实测 64.9%。

这类优化对重复系统提示词、固定文档前缀和多轮会话尤其有价值，但必须先确认实际请求的前缀复用率。

## 结论与边界

这组数字只说明这套硬件、模型、量化格式和参数组合下发生了什么。换模型、换驱动、换 batch 或换后端，结论都需要重新测。
