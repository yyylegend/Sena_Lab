单卡部署大模型时，最先遇到的问题往往不是“哪个参数更快”，而是“模型到底能不能完整放进显存”。

这组实验使用 22GB 的 RTX 2080 Ti，模型为 Qwen3.5-9B AWQ。结论不打算推广到所有硬件和模型，只记录这一组条件下，显存、速度和上下文长度之间如何互相制约。

## 先算显存，才能谈优化

推理显存主要花在三处：

- 模型权重；
- KV Cache 或混合架构中的状态池；
- CUDA context、计算缓冲和推测解码带来的固定开销。

Qwen3.5-9B AWQ 的 LLM-only 权重约为 10.35 GiB，给 KV Cache 留出了足够空间。相比之下，大多数 27B AWQ 或 INT4 模型的权重已经接近 19 到 22GB，在这张卡上几乎没有余量。

显存账如果没有先算清，后面的优化很容易变成碰运气：模型勉强启动，不代表所有层都在 GPU 上，也不代表上下文长度还有可用空间。

## 哪个设置真正带来了速度变化

在 8K 上下文、单序列、生成 256 tokens 的相同条件下，测试结果如下：

| 配置 | 速度 |
| --- | ---: |
| eager 基线 | 41.0 tok/s |
| 加入 CUDA Graph | 46.1 tok/s |
| MTP_K=2 | 80.3 tok/s |
| 只提高 MAX_BATCHED_TOKENS | 80.8 tok/s |

CUDA Graph 带来了稳定但有限的提升。真正拉开差距的是 MTP：草稿头先预测少量 token，主模型一次验证多项候选，减少了主模型反复读取权重的次数。

相反，单独增大 MAX_BATCHED_TOKENS 几乎没有变化。这说明当前瓶颈不在这个参数，继续围绕它调优没有价值。

## 长上下文和推测解码不能同时贪心

在这组硬件和模型上，262K 上下文可以运行，显存占用约为 21998 / 22528 MiB，生成速度为 38.6 tok/s。长上下文本身没有想象中昂贵，因为模型的混合注意力结构降低了部分缓存成本。

但 MTP 会额外占用验证工作区。上下文拉得很长时，显存余量已经很小，再开启推测解码就需要牺牲可用 KV 空间。

这不是参数冲突，而是资源预算：速度和上下文都在争同一块显存。

## Prefix Cache 更适合重复前缀

对约 6.9K tokens 的长前缀做冷、热请求比较，响应时间从 3.30 秒降到 0.71 秒，约为 4.6 倍提升。引擎 hit rate 为 64.9%。

这个结果并不意味着所有请求都会变快。它依赖前缀足够长、内容足够相似，并且缓存块刚好能够命中。系统提示词、固定文档前缀和多轮会话通常更适合这类优化。

## 这组实验能说明什么

实验说明了一个很实际的顺序：先确认模型、权重和上下文能否装下，再测试单一优化是否真的改变瓶颈，最后才讨论并发和吞吐。

换模型、换驱动、换量化格式或换后端后，所有数字都需要重新测量。
