## 这次要解决什么

一个请求大致会经历：

1. API 接收请求；
2. 后端不断返回生成片段；
3. 收到最后一个片段；
4. 删除这个请求的临时记录。

可以把临时记录理解成餐厅的“正在处理订单”清单。菜已经端出去以后，订单也必须从清单里删掉。否则请求量一多，服务会误以为还有很多请求没有完成，后续的 `inflight` 指标也会失真。

这正是 Day 4 要先验证的边界。Prometheus 指标放在 Day 5 再接入，先保证被统计的生命周期本身是正确的。

## 测试范围

测试文件：`tests/observability/test_frontend_metrics.py`

| 测试场景 | 需要确认的事情 |
|---|---|
| 流式 `/generate` | 返回所有片段和 `[DONE]`，结束后清理请求记录 |
| 流式 ChatCompletion | 返回角色块、结束块和 `[DONE]`，结束后清理请求记录 |
| 非流式 ChatCompletion | 收集到最终 reply 后返回完整内容，并清理请求记录 |
| 客户端断开 | 只发送一次 `AbortMsg`，并清理请求记录 |

测试使用假的收发队列，把 `UserReply` 直接送给 `FrontendManager`。这样测试关注的是 API 层的请求状态，不会被模型加载、显存、GPU kernel 或 ZMQ 环境干扰。

## 第一轮：先测试，发现问题

修复前的结果：

```text
3 failed, 1 passed
```

通过的是客户端断开场景。三个正常完成场景都发现同一个问题：回答内容已经返回，但 `ack_map` 和 `event_map` 里的请求记录仍然存在。

问题原因在于：

- `wait_for_ack()` 原本把清理代码放在生成器循环之后；
- 三个调用方收到最终 reply 后立即 `break`；
- 内层生成器没有继续执行到清理位置。

所以这不是“模型没有回答”，而是“回答完以后忘了收尾”。

## 修复内容

修改文件：`python/minisgl/server/api_server.py`

做了三处最小修改：

1. 给 `wait_for_ack()` 加上 `try/finally`，无论正常结束还是取消，都尝试清理 `ack_map` 和 `event_map`；
2. 使用 `pop(uid, None)`，让重复清理不会再次抛错；
3. 流式和非流式调用方不再在最终 reply 处提前 `break`，让 `wait_for_ack()` 自然结束并完成清理。

API 返回内容没有改变，改动只影响请求结束后的内部状态。

## 这次实验说明了什么

现在可以确认：

- 流式请求能够正常结束；
- 非流式请求能够正常结束；
- 客户端取消能够正常清理；
- 正常完成和取消都不会留下请求状态。

这次还没有测 TTFT、ITL、吞吐或显存，也还没有真正输出 Prometheus 指标。因此它是一次 API 生命周期正确性测试，不是性能实验。
