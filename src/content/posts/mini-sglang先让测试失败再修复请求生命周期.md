这次实验没有测 GPU 性能，也没有启动真实模型。目标很窄：确认 API 请求在正常结束、流式结束、非流式结束和客户端断开后，都能清理自己的临时状态。

## 问题是什么

请求大致经过四步：

1. API 接收请求；
2. 后端持续返回生成片段；
3. 收到最终结果；
4. 删除这个请求的临时记录。

如果第四步漏掉，回答表面上仍然能返回，但系统里的 inflight 记录会越来越多，后续指标也会失真。

## 先让测试失败

我用假的收发队列和假的 UserReply，把测试范围限制在 API 层，不启动 GPU、模型或真实 ZMQ。

第一轮结果是：

    3 failed, 1 passed

三个正常完成场景都有同一个问题：内容已经返回，但 ack_map 和 event_map 里的请求记录还在。客户端断开场景反而通过了。

原因不是模型生成失败，而是生成器的控制流没有走到清理代码：

- wait_for_ack 原本把清理放在生成器循环之后；
- 调用方收到最终 reply 后直接 break；
- 内层生成器没有继续执行到清理位置。

## 最小修复

修复只动了三个地方：

- 给 wait_for_ack 的清理逻辑加上 try/finally，保证正常结束和取消都能执行；
- 使用 pop(uid, None)，让重复清理不会再次抛错；
- 调用方不在最终 reply 处提前 break，让生成器自然结束。

API 返回内容没有改变，改动只影响请求结束后的内部状态。

## 修复后的结果

第二轮标准 pytest 结果为 4 个测试全部通过，同时通过了 Python compileall 和 git diff --check。

这次实验没有得到 TTFT、ITL、吞吐或显存结论。它只证明 API 请求生命周期的清理逻辑正确，性能实验要在这条基础上继续做。

## 我从这次问题里得到的判断

可观测性不是最后再加几个 Prometheus 指标。先要保证被统计的状态本身正确，否则指标只是把错误记录得更整齐。
