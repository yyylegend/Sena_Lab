流式接口最容易让人误以为“看到回答就算结束”。

实际上，客户端收到最后一个 token 之后，服务端还要做一件事：清理这次请求留下的临时状态。否则，系统会继续把已经完成的请求算作进行中，后续的 inflight 指标、取消逻辑和资源统计都会失真。

这次测试只关注这个收尾动作。

## 先把问题缩小到 API 层

测试没有启动 GPU、模型或真实 ZMQ，而是使用假的收发队列和假的 UserReply，把变量收缩到请求生命周期本身。

覆盖的场景包括：

- 流式 generate；
- 流式 ChatCompletion；
- 非流式 ChatCompletion；
- 客户端中断。

每个场景都需要确认两件事：回答是否正常返回，以及完成后对应的 ack_map 和 event_map 是否被清理。

## 第一轮测试暴露了什么

第一轮结果为 3 failed、1 passed。

通过的是客户端断开场景。三个正常完成场景都有同一个问题：最终内容已经返回，但请求记录仍然留在内存里。

原因在于生成器的控制流。wait_for_ack 原本把清理逻辑放在循环之后，而调用方在收到最终 reply 后立刻跳出循环，内层生成器没有机会继续运行到清理位置。

表面上看，接口返回完全正常；从服务端状态看，这个请求却从未真正结束。

## 修复不是增加一个 if

修复把清理逻辑放进 try/finally，保证正常结束和取消都能进入收尾阶段。清理操作使用 pop(uid, None)，即使同一条记录被重复处理也不会再次报错。

同时，调用方不再在最终 reply 处提前跳出，让生成器自然结束。

API 返回内容没有变化，改动只影响请求结束后的内部状态。

## 修复后如何确认

第二轮测试中，四个场景全部通过，同时通过了 Python compileall 和 git diff --check。

这次没有测试 TTFT、ITL、吞吐或显存，因此不能把它描述成性能优化。它验证的是更基础的一件事：任何后续指标都建立在请求状态正确的前提上。

可观测性并不是最后再挂几个 Prometheus 指标。先确认系统知道一个请求何时开始、何时结束，才谈得上统计它用了多久、失败在哪里。
